## 数据合成思路

为了快速构建一些强度足够（在特定LLM Coding Agent下面成功概率>0且<=某个%）的Coding任务

参考过往内部数据合成的做法，我采取了以下几个策略:

1. 针对具体代码仓库构建基准环境 
从开源代码仓库和稳定主流的Docker img环境（一般选择Ubuntu Stable Release）出发，先让通用的Coding Agent实现一个正确完成项目构建基准环境；
假如基准环境的构建不稳定，那么我们就有了一个基准强度的数据集合；

2. 从基准环境出发能够提高足够反馈的代码测试环境
一般来说我们要求代码测试环境能够至少成功执行自带的部分单元测试，或者在没有单元测试的情况下编写至少一个单元测试；
构建准确的测试环境我们还要求能够构建覆盖率等精确到文件、代码行级别的测试质量评估指标；
不管基准环境、测试环境还是后续迭代的版本，我们都要以完整的docker img作为输出产物；

3. 根据issue，代码缺陷报告等seed样本逐步提高强度
大概的做法是：
3.1. 先给予Coding Agent足够的执行+反馈次数loop，从稳定可成功的issue或者缺陷测试出发，保证任务的可执行性；
3.2. 评估基础任务的执行成功率，判断任务执行成功的测试标准是否存在强度过高或者过低的情况；
3.3. 通过限制Coding Agent在成功样本上的执行次数，或者增加策略限制，逐步构成成功概率更低和更难的任务样本；
3.4. 重复3.2和3.3，直到达到目标强度；
3.5. 在达到目标强度后，通过AI muation要求增加任务变种：例如在原本的任务基础上增加额外的要求，从而扩大样本总数；

## 具体案例example_1

example_1这里的本质代码缺陷是利用了LLM的一个常见的缺陷：
“即在关键词匹配到失效的代码、文档的情况片段下不作进一步求证即开始执行”

具体来说，xgrammar当前版本有一个：XGRAMMAR_ENABLE_COVERAGE选项，这个选项会频繁匹配到LLM的搜索，但这个选项实际无效；
这个错误会导致Coding Agent构建测试测试环境下一定概率失败。

而我们通过限制Coding Agent在成功样本上的执行更少的次数，可以逐步构成成功概率更低和更难的任务样本；

这个例子当中如果限制执行docker build（重新构建）的次数<=2，那么在kimi-k2.5+claude code下面成功概率就约为50%
而限制为“仅可一次构建”的情况下，成功概率就远低于40%，但我们需要校验这个限制强度上测试有成功的可能；
